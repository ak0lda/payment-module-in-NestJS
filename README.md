# Payments service

Тестовый платёжный сервис на NestJS и PostgreSQL. Что он умеет:

- повторный запрос с тем же `Idempotency-Key` не создаёт второй платёж;
- повторно пришедший вебхук ничего не меняет;
- статус меняется в транзакции, под блокировкой строки и только по допустимым переходам.

## Запуск

```bash
cp .env.example .env
docker compose up -d
npm install
npm run start:dev
```

Сервис на `http://localhost:3000`. Тесты: `npm test`, линтер: `npm run lint`.

Схема создаётся из `init.sql` только при первом старте с пустой базой. Если схема поменялась, базу нужно пересоздать: `docker compose down -v`.

## Примеры

Создать платёж:

```bash
curl -i -X POST http://localhost:3000/payments \
  -H "Content-Type: application/json" \
  -H "Idempotency-Key: key-1" \
  -d '{"amount": 10000, "currency": "RUB"}'
```

Первый раз вернётся `201` и платёж в статусе `pending`. Если повторить команду, вернётся `200` и тот же платёж. Без заголовка `Idempotency-Key` или с неверным телом будет `400`.

Получить платёж: `curl -i http://localhost:3000/payments/<id>` (`200` или `404`).

Вебхук. `provider_payment_id` берётся из ответа на создание платежа:

```bash
curl -i -X POST http://localhost:3000/webhooks/provider \
  -H "Content-Type: application/json" \
  -d '{"event_id": "evt-1", "provider_payment_id": "prov_...", "status": "succeeded"}'
```

- первый вызов: `200`, платёж стал `succeeded`;
- тот же `event_id` ещё раз: `200`, ничего не меняется;
- `failed` после `succeeded` с новым `event_id`: `200`, статус остаётся `succeeded`, в логе предупреждение;
- неизвестный `provider_payment_id`: `404`, провайдер повторит позже.

## Как работает вебхук

Всё в одной транзакции:

1. Находим платёж с `SELECT ... FOR UPDATE`. Нет платежа: откат и `404`.
2. Пишем событие в `webhook_events`. Если такой `event_id` уже есть, выходим с `200`.
3. Проверяем переход статуса в `resolveTransition`. Недопустимый: лог и `200`.
4. Обновляем статус и коммитим.

Порядок шагов не такой, как в ТЗ: платёж ищется до записи события, потому что `payment_id` в `webhook_events` обязателен и без найденного платежа событие не записать. Для неизвестного платежа событие по-прежнему не сохраняется.

Дубль события отсекается через `ON CONFLICT DO NOTHING`, а не через ошибку 23505. После ошибки Postgres не даёт продолжить транзакцию.

## Почему так

- Копейки вместо float: float не хранит 0.1 точно, целые числа считаются без ошибок.
- Уникальный индекс вместо проверки в коде: «проверить и вставить» это два шага, между ними может влезть другой запрос. Индекс срабатывает атомарно.
- `FOR UPDATE`: транзакция сама по себе не мешает другим читать ту же строку. Без блокировки два вебхука прочитают `pending` и перезапишут друг друга. С блокировкой второй ждёт и видит уже новый статус.
- При ошибке вебхук получает не 2xx: 2xx для провайдера значит «принято», повторять он не будет. Не 2xx значит «пришли ещё раз», а транзакция откатилась, так что повтор обработается с нуля.
